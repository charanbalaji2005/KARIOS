# P1 and P2

What the audit's Priority 1 (complete the platform) and Priority 2 (performance and observability) lists asked for, what got built, and what did not.

The short version: **the backend is done, most of the dashboard is not.** Auth, admin, OpenAPI, import/export, metrics, tracing, load testing and Grafana all exist and work. Of the thirteen dashboard pages asked for, three were built.

---

## P1 — platform

### MFA / TOTP ✅

RFC 6238, implemented directly (`lib/totp.ts`) rather than pulled from a dependency — the algorithm is forty lines of HMAC, and the decisions that actually matter are ones this code should make visibly.

Three of those decisions:

- **±1 step window.** Wider windows are the usual "fix" for clock skew, and each extra step is another 30 seconds an intercepted code stays valid.
- **Steps are single-use.** The accepted step is recorded, and a replay of the same code is refused. Without this, a code captured from a phishing page is good for the rest of its window — which is the whole attack.
- **Enrolment is two steps.** The secret exists once the QR is shown; MFA is not enforced until the user proves they can generate a code. Skipping this is how people lock themselves out of accounts by scanning a QR into an app they then delete.

Backup codes are hashed (not encrypted — the server only ever checks one), single-use, and use an alphabet without `0/O` or `1/I/L`, because they get transcribed off a printout by someone already locked out and irritated.

Disabling MFA requires the **password**, not just a session: a stolen session token should not be enough to remove the control that exists to make stolen session tokens less useful.

Login gains a middle state — correct password, MFA required, no session — whose challenge token lives in Redis and is destroyed on first use. A signed JWT would be replayable for its full lifetime.

RFC test vectors are in `tests/integration/totp.test.ts`. An authenticator that is subtly wrong still emits six plausible digits.

### OAuth — Google and GitHub ✅

Authorization Code + PKCE + `state` + `nonce`. What each is for, since they get copied around without it:

| | Prevents |
| --- | --- |
| `state` | login CSRF — an attacker completing their own authorization and feeding you the code, logging you into *their* account |
| PKCE | a leaked code (Referer header, proxy log) being redeemable by anyone else |
| `nonce` | an ID token replayed from another session |

`state` and the verifier are stored server-side, not in a cookie, because a cross-site redirect back from the provider is exactly where Safari will have dropped the cookie.

Two things worth calling out:

**Accounts are linked by verified email only.** Both sides verified is what makes it safe; without that check, registering an unverified address matching an existing user is an account-takeover primitive.

**The session is handed over as a one-time ticket, not a token in the URL.** URLs end up in history, Referer headers and proxy logs, and a token there outlives the redirect. The ticket has a 60-second life and dies on redemption.

`password_hash` is now nullable — an OAuth account has no password and must not be given a fake one, which would be a guessable credential.

### Organization invitations ✅

The invariant: **an invitation is an offer to an address, not a link that works for whoever holds it.** Acceptance checks the signed-in user's email against the invited one, so a forwarded email is not a free membership.

Also: only the token hash is stored; re-inviting replaces rather than stacks (several live tokens for one address is several ways in); nobody can invite above their own role (an admin minting an owner who then removes them is privilege escalation by way of a helpful form); and an organization cannot lose its last owner, because there is no support desk here to fix that.

### Admin surface ✅ (API), ❌ (UI)

`users.is_platform_admin` replaces the `PLATFORM_OPERATORS` email allow-list, which was always a placeholder. The env var now only *bootstraps* the first admin at startup — a fresh install needs one, and the alternative is telling people to edit rows by hand. Existing admins are never demoted from the env, because a variable that silently removes access on restart is a nasty surprise during an incident.

Admin status is read from the database per request, not from a token claim, so revoking it takes effect immediately.

Endpoints: overview, users, projects by size, security events, grant/revoke admin, suspend a project. Suspension sets every quota to zero rather than deleting anything — which is why zero and `NULL` are kept distinct in the quota code.

Three rules the surface follows: read broadly, write narrowly; audit everything including the reads that expose other people's data; and destructive actions require typing the name, not clicking a confirm dialog.

The admin *pages* are not built.

### OpenAPI 3.1 ✅

Generated from `information_schema` and `pg_catalog`, not maintained by hand — a hand-written spec is wrong the first time someone adds a column, and a confidently wrong spec is worse than none because people write code against it.

`GET /projects/:ref/openapi.json`, `/docs` (Scalar), `/openapi.types`.

Two details that make a generated spec usable rather than merely present: `bigint` is typed as a string (past 2^53 it does not survive `JSON.parse` as a number, and silently losing precision is worse than an inconvenient type), and a `NOT NULL` column with a default is not marked required (a spec demanding `id` on every POST is one people stop trusting immediately).

### CSV / JSON import and export ✅

Export streams and quotes defensively: values beginning `=`, `+`, `-` or `@` are quoted, because CSV injection is how an exported support ticket runs a command on someone's laptop.

Import **does not stream**, deliberately. It validates everything first and runs the whole file in one transaction, because a half-applied import is worse than a rejected one — you cannot tell which rows landed without diffing against the source. `dryRun` is the default and returns the same shape as the real run, so the UI needs one code path rather than two.

The CSV parser is hand-written (RFC 4180: quoted fields, escaped quotes, CRLF). Splitting on commas works until the first address column. An empty cell is `NULL`, not `""` — getting that backwards turns every missing number into a type error.

### API explorer ✅

A request builder against the project's own REST surface. Timing is measured **in the browser**, so it includes the network — a server-side number flatters the platform and is not what the developer's code will experience. Using a `service_role` key raises a warning, since that key bypasses the policies the page exists to help verify.

### Relationship diagram ✅

Plain SVG, laid out by foreign-key depth — tables depending on nothing on the left, their dependents to the right. No graph library: the problem is small and specific, and a layered layout in eighty lines beats a dependency that brings its own canvas and event model. Cycles (self-references, genuine loops) terminate rather than recursing forever.

### Storage UI ✅

Buckets, files, upload, signed links, delete. Uploads go straight to the API as `FormData` rather than through a Next.js route handler, so a large file streams once instead of being buffered by an intermediate hop and inflated a third by base64.

### CLI and SDK ✅

Done in the previous pass.

## P2 — performance and observability

### Per-endpoint p50/p95/p99 ✅

`lib/metrics.ts`. Latency goes into **fixed bucketed histograms**, not retained samples: memory is proportional to the number of routes, not the volume of traffic. The naive approach makes monitoring heaviest exactly when the machine is busiest, which is the wrong shape for a laptop.

The approximation is worth naming: a p99 read from a histogram whose top bucket is `+Inf` tells you "above 5 seconds", not how far above. Good enough to alert on; not precise enough to chase one pathological request — that is what the query log and EXPLAIN are for. The endpoint says so rather than letting someone over-trust the number.

Buckets are Prometheus-compatible and quantiles use the same linear interpolation as `histogram_quantile`, so the dashboard and Grafana agree rather than differing by a few percent for reasons nobody can explain.

There is a cardinality guard at 500 series. An unbounded label — a raw URL with ids in it — turns the registry into a memory leak that looks like slow resource exhaustion.

### Prometheus expansion ✅

Added: request counts and errors by route and status, per-route duration histograms, connection budget and **clients waiting** (the number that actually predicts an outage — a pool at capacity is fine until something queues behind it), Redis hit ratio and memory, active projects, quota refusals, unverified backups, webhook failures.

### Tracing ✅ (partial, deliberately)

`plugins/observability.ts` accepts or creates a W3C `traceparent`, echoes it, and attaches the trace id to slow and failed log lines. That is the useful 20% of distributed tracing with no collector: one id joining the nginx log, the API log and the query log for a single request.

A full OTLP exporter is **not** here, and that is a choice rather than an omission. It needs a collector process, and a collector that is not running silently drops spans — which looks exactly like tracing working until the moment you need it.

Only slow (>1s) or failed requests are logged in full. Logging every request at info on a laptop fills the disk the database needs.

### Grafana ✅

`infrastructure/monitoring/grafana/kairos-overview.json`, nine panels, importable. Alert rules stay in Prometheus rather than Grafana so alerting survives Grafana being down.

### Load testing ✅

`tests/benchmark/load.bench.ts` steps concurrency through a ladder and finds the **saturation point** — where throughput stops rising while latency keeps climbing. That is the number that matters for a machine you can carry, and a fixed-concurrency benchmark cannot find it. It samples server CPU and memory mid-stage, not after, because afterwards the machine has recovered and the reading describes an idle box.

Errors at high concurrency are usually the connection budget doing its job, and the output says so — refusing one project is the intended behaviour, not a bug.

### Query plan analysis ✅

`POST /projects/:ref/sql/explain`. Refuses `ANALYZE` on anything that writes, because "let me just check the plan" should never be how a DELETE gets executed.

The findings are the point. It flags sequential scans over large tables, estimates off by more than 10x (a statistics problem, not an index one — different fix, so worth distinguishing), and sorts that spilled to disk.

### PostgreSQL tuning ✅

Done previously (`scripts/tune-postgres.sh`).

## Not built

**Dashboard pages:** admin, webhooks, backups/restore, logs, analytics, settings, members/invitations. The APIs for all of these exist and are documented; the pages are not written.

**GraphQL.** The audit marked it optional and it is the right thing to skip while the core is still settling.

**Full OpenTelemetry.** Reasoning above.

**Storage advanced features:** versioning, resumable/multipart uploads, range requests, lifecycle rules, virus-scanning hook.

**Visual query builder, PgBouncer, read replicas, Kubernetes.** All P3, none of them urgent for a single machine.

**Verification.** None of this has been run against a live stack. Typecheck is clean and the unit tests pass; the integration and E2E suites need Docker, and the OAuth flows need real provider credentials. Treat every "✅" above as "written and type-checked", not "observed working".
